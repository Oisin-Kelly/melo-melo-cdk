# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MeloMelo is a serverless private music sharing and social platform built with AWS CDK in C#. The backend uses Lambda (native AOT on ARM64), DynamoDB (single-table design), Cognito, HTTP API v2, and S3. The frontend (`web/`) is a React SPA — Vite + TypeScript, built on the **Astryx design system** (`@astryxdesign/core` components + StyleX + the `theme-neutral` theme) — served from S3 + CloudFront by `web-stack`.

## Build & Deploy Commands

```bash
# Build CDK infrastructure
dotnet build infra/MeloMeloCdk.csproj

# Build all projects
dotnet build MeloMelo.sln

# Synthesize CloudFormation templates
cdk synth

# Deploy (set ENVIRONMENT=dev or prod)
ENVIRONMENT=dev cdk deploy --all

# Fast deploy when many lambdas changed (one docker run, parallel publishes,
# then bundling just copies the prebuilt binaries):
./scripts/build-lambdas.sh && USE_PREBUILT=1 ENVIRONMENT=dev cdk deploy --all

# Deploy a specific stack
ENVIRONMENT=dev cdk deploy data-stack-dev

# Diff before deploying
cdk diff

# Unit tests (pure logic + validators always; repository tests need DynamoDB Local, else they skip)
docker run -d -p 8000:8000 amazon/dynamodb-local
dotnet test --project api/Tests/Adapters.Tests
dotnet test --project api/Tests/Lambda.Tests     # handler tests, mocked dependencies, no Docker

# Frontend: dev server (env from web/.env.local — copy web/.env.example, fill from cdk deploy outputs)
cd web && npm run dev

# Frontend: build + typecheck + lint
cd web && npm run build && npm run lint

# Frontend: unit tests (Vitest + jsdom, network mocked by MSW — no AWS)
cd web && npm test                # or test:watch / test:coverage

# Frontend: build against deployed backend outputs + deploy web-stack
./scripts/deploy-web.sh
```

Lambdas are built automatically during `cdk deploy` via Docker (`dotnet publish -c Release -r linux-arm64` with AOT). Each function's asset is scoped to the sources it compiles (its own folder + `Lambda.Shared` + `Ports`/`Adapters`/`Domain`, excluding `bin`/`obj`), so only Lambdas whose inputs changed get rebuilt — editing shared `Adapters/` code rebuilds everything, editing one Lambda rebuilds one. Bundling is sequential (CDK has no parallel-bundling option). Always run `cdk` from the repo root.

## Architecture

**Solution layout:** `MeloMelo.sln` at root.

- `infra/` — CDK stacks (.NET 10.0). Entry point: `Program.cs` orchestrates 6 stacks:
  - `data-stack` — DynamoDB table with GSI1, GSI2, and GSI3 (GSI2 reuses `GSI1PK` as its hash key with a distinct `GSI2SK` sort key; GSI3 has its own `GSI3PK`/`GSI3SK` keys, used for a user's own tracks, playlists, and albums newest-first, plus the username search index)
  - `storage-stack` — S3 buckets (dropbox, private, public)
  - `lambda-stack` — HTTP API + Cognito trigger Lambda functions + IAM permissions
  - `auth-stack` — Cognito user pool + triggers
  - `sfn-stack` — Step Functions state machine, `ProcessTrackLambda`, and audio processing layers (owns `ProcessTrackLambda` to avoid a cross-stack dependency cycle with `lambda-stack`)
  - `api-stack` — HTTP API v2 routes + Cognito authorizer
  - `web-stack` — frontend hosting (private S3 bucket + CloudFront with OAC, SPA fallback 403/404 → index.html). Only instantiated when `web/dist` exists (its `Source.Asset` would otherwise break backend-only synth/deploys and CI) — build via `scripts/deploy-web.sh`
- `api/` — Lambda code (.NET 10.0), hexagonal architecture:
  - `Domain/` — Entities: User, Track, UserFollow, SharedTrack, Playlist, Like, Album, ProcessTrack, PaginatedResult (+ the HTTP request records)
  - `Ports/` — Interfaces, split into `Repositories/` (namespace `Ports.Repositories` — one interface per aggregate/responsibility: IUserRepository (profile, seen markers, search, recipient validation) vs IFollowRepository (follow graph); ITrackRepository vs ISharedTrackRepository (direct shares + the access rule); IAlbumRepository (album meta + delete) vs IAlbumTracklistRepository (ordered memberships) vs IAlbumShareRepository (shares, grants, shared-with-me); …), `Services/` (`Ports.Services` — IDynamoDBService, IS3Service, IAudioService, IImageService, IUserPoolService), and `Validation/` (`Ports.Validation` — the four I*ValidationService)
  - `Adapters/` — AWS implementations of Ports, mirroring the same split: `Repositories/` (`Adapters.Repositories`, incl. `TrackBatchLookup` + `UpdateExpressionBuilder`), `Services/` (`Adapters.Services`), `Validation/` (`Adapters.Validation`, incl. `InputSanitiser`). Namespaces match folders.
  - `Lambda/Lambda.Shared/` — Base handler with Ok/Accepted/Error response helpers
  - `Lambda/{Auth|User|Track|Playlist|Album|Feed|Activity}/*Lambda/` — Individual Lambda functions (each a separate executable), grouped by domain: `Auth/` (Cognito triggers), `User/` (profile, follows, progress, seen markers), `Track/`, `Playlist/`, `Album/`, `Feed/` (home feed), `Activity/` (activity feed)
  - `Lambda/Layers/` — Binary layer zips (ffmpeg, ffprobe — linux-arm64 static builds) for audio processing
- `web/` — React SPA (Vite + TypeScript) built on the **Astryx design system**, organised as **bulletproof-react** (see `web/README.md` for the full structure). Two layers of conventions, both worth reading before touching frontend code:

That one hook is what makes old id routes (`/tracks/:id`, `/albums/:id`, `/playlists/:id`, kept for shared links and pre-slug items), old slugs after a URL change, and `/u/:username…` (→ `OldProfileRedirect`) all land on the readable URL. Items without a slug link by id. The edit dialogs have a URL field (`components/forms/SlugField`, rules in `forms/slug.ts`, limit `LIMITS.slug`) that sends `slug` only when changed.
  - **Offline / installable**: `public/sw.js` is a hand-written service worker (production only, registered in `main.tsx`): install saves index.html + every asset it references, navigations are network-first falling back to the saved index.html, `/assets/*` cache-first (hashed names) — so MeloMelo opens offline and `OnlineGate` shows the offline screen; API calls (other origin) are never touched. `public/manifest.webmanifest` makes it installable. web-stack serves `sw.js` + the manifest no-cache like index.html (a year-long immutable cache would pin users to an old worker); the icons get a week's cache. **Link previews (Open Graph)**: chat-app crawlers don't run JS, so every URL unfurls as one generic card — the tags are injected by a small plugin in `vite.config.ts` (image `public/og-image.png`, 1200×630, absolute via `VITE_SITE_URL`, which `scripts/deploy-web.sh` reads from web-stack's `WebUrl`; relative on the very first deploy); `og-image.png` gets the icons' week cache. Per-link cards would need a CloudFront behaviour for `/s/*` → a public Lambda that inserts tags into index.html — deferred.
  - **Page canvas**: `<html>` restates the theme's background in `app/global.css` (the tokens only exist inside `<Theme>`) so overscroll/safe areas match the screen: `--color-background-surface`'s pair when the signed-in AppShell is showing (`html:has(.astryx-app-shell)`), `--color-background-body`'s otherwise (landing, auth, invites); `ThemeModeProvider` sets its `color-scheme` to the chosen mode.
  - **Long user text**: `app/global.css` sets `overflow-wrap: anywhere` on body, so an unbroken run (a pasted link, "aaaa…" to the limit) wraps instead of widening its box and scrolling the page sideways; Astryx `Text` sets its own `break-word` (which still sizes the box to the run), so `.mm-expandable-text` restates `anywhere`.
  - **Styling escape hatch**: things no Astryx component does (Borel wordmark, gradient blobs, cover art, badge anchoring, search field width) are small co-located `.css` files written only against tokens — the same approach the Astryx templates' own `<style>` blocks take (there's no StyleX compiler, so `xstyle` isn't available).
  - **Unit tests**: Vitest + jsdom + Testing Library, co-located `*.test.ts(x)` with helpers in `src/testing/` (see `web/README.md` → Unit tests). MSW is the only network and an unhandled request fails the test; Amplify and `sileo` are mocked. Hooks/API modules are tested through real TanStack Query against MSW handlers (asserting request shape, cache keys, optimistic updates + rollback, invalidations); screens through Testing Library with the real Astryx components (`setup.ts` stands in for `<dialog>`/popover/`matchMedia`). Field errors render twice (field + Astryx's hidden `role="alert"` announcer) — assert with `testing/messages.ts`. `validation.test.ts` reads `api/Domain/ReservedUsernames.cs` and fails if the client's reserved-username list drifts from it. Test files are type-checked by `tsconfig.test.json` (included in `tsc -b`); CI's `web-tests` job (lint + types + tests) gates e2e alongside `unit-tests`.
  - **UI e2e**: `e2e/ui/` (Playwright `ui` project, `WEB_BASE_URL` → dev server or CloudFront); `fixtures/page.ts` signs in through the real login form.

**Lambda pattern:** Each Lambda has `Function.cs` (handler with `[LambdaFunction]`/`[HttpApi]` attributes, constructor DI), `Startup.cs` (DI registration via `[LambdaStartup]` — the data layer is one call, `builder.Services.AddMeloMeloData(tableName)` from `Adapters/ServiceCollectionExtensions.cs`, which registers the DynamoDB client/service and **every** repository; Startups only add their S3/image/audio/validation services), and AOT JSON serializer context. Step Function-invoked Lambdas (`ProcessTrackLambda`) skip `[HttpApi]` and `BaseLambdaFunctionHandler`, taking a plain input record and returning a plain output record.

Two Cognito trigger Lambdas (PostConfirmation, CheckEmailExistence), a growing set of HTTP API Lambdas (users, follows, tracks, playlists, likes, albums — including recipients endpoints — and share links), one Step Function-invoked Lambda (`ProcessTrackLambda`). Every HTTP route is behind the Cognito authorizer **except `GET /links/{token}`** (the share-link invite preview, `HttpNoneAuthorizer`, throttled on its own via the default stage's route settings).

`DELETE /tracks/{trackId}` (owner-only) removes the track's whole footprint in retryable order: album memberships + their grants, the S3 audio file + cover, then likes (each with a guarded transaction that also decrements the liker's likes-playlist `trackCount`/`totalDurationSeconds`), direct shares/remaining grants/upload status, and the Track item last. Playlist references (any user's) are left dangling on purpose — in a **custom** playlist they surface as removable `unavailable` placeholders (reason `DELETED` when the track is gone, `REVOKED` when access was withdrawn), rendered from the membership's denormalized name/duration; the likes playlist has no denormalized name, so deleted liked tracks are dropped. `GET /playlists/{id}` returns `tracks.items` as `PlaylistTrackEntry` (available entries carry the full `track`).

Playback: `GET /tracks/{trackId}/stream` (`GetTrackSegmentsLambda`) returns a single 6-hour presigned GET URL for the track's one processed AAC file in the private bucket (`processed/{trackId}/audio.m4a`, served `audio/mp4`), gated on the standard track-access rule — the client range-requests directly from S3 (the file is encoded with `+faststart` so seeking works without downloading the whole thing). The 6h expiry outlasts a single sitting; a resume days later just re-fetches. (The Lambda folder/construct keeps its `GetTrackSegments` name to avoid infra churn.) **Original download:** `GET /tracks/{trackId}/original` (`GetOriginalTrackLambda`, **owner-only** — recipients get the usual 404) HEADs the archived upload (`processed/{trackId}/original`, kept byte-for-byte with its upload Content-Type) and returns `{url, fileName, contentType, expiresAt}`: a 5-minute presigned GET whose `ResponseHeaderOverrides.ContentDisposition` makes S3 serve it as an attachment named `{track name}.{ext}` (`Domain/OriginalDownloads`: the extension comes from the content type — the upload's filename was never stored; when the browser sent no usable audio type (e.g. `application/octet-stream` for a .flac) `ProcessTrackLambda` accepts and archives it under the type its staged key's extension implies (`OriginalDownloads.AudioContentType`) — names are made filesystem-safe, and the header carries an ASCII fallback + RFC 5987 UTF-8 name). Tracks processed before originals were archived have none → 404 "The original file isn't available for this track". The web track page's owner ⋯ menu has **Download original** (`useDownloadOriginal` → `lib/download.ts` `startDownload`, a plain navigation — no CORS).

## Playlists, Likes & Albums

- **Readable URLs (slugs)**: tracks, albums and custom playlists have a per-owner, per-kind unique slug (`USER#{owner}` / `SLUG#{KIND}#{slug}` → `targetId`; canonical one on the meta item's `slug`), claimed from the name on create (`SlugRecords.ClaimAsync`: `base`, `base-2`…, guard `attribute_not_exists OR targetId = :self` so retried uploads reuse theirs; reserved track slugs like `followers`/`albums` skipped — `Domain/Slugs.cs`). **Renaming never changes it**; an explicit `slug` on the update PUTs claims the new record in the same transaction (taken → 400) and the old record stays as a redirect; deletes remove every slug record before the meta item. `GET /users/{username}/slugs/{kind}/{slug}` (`ResolveSlugLambda`) returns `{id, slug}` only past the item's normal access check — every miss is the identical 404. Usernames can't be top-level app paths or web file names (`Domain/ReservedUsernames`, checked by the PreSignUp trigger). Pre-slug items: `scripts/backfill-slugs.sh`; clashing pre-existing usernames: `scripts/check-reserved-usernames.sh`. Full rules in `docs/data-model/README.md`.
- **Playlists** are always private. Every user has a built-in likes playlist (reserved id `likes`, type `LIKES`, created at PostConfirmation) that cannot be renamed/deleted; custom playlists (type `CUSTOM`, server-generated ids) are editable and deletable. Playlists may contain any track the user can access.
- **Cover images**: playlists and albums accept an optional `imageKey` on create/update (staged in the dropbox bucket), processed by `ImageService` to a 400×400 JPEG in the public bucket (`playlists/{id}/cover_400x400.jpg` / `albums/{id}/cover_400x400.jpg`) with a dominant-color hex (`imageBgColor`) — same flow as track covers and profile images. `clearedImage: true` on update removes them; deletes clean up the cover object.
- **Likes** (tracks and albums) are stored target-side (`TRACK#{id}`/`LIKE#{user}`, `ALBUM#{id}`/`LIKE#{user}`) so owners can see who liked; `likeCount` lives on the Track/Album item, maintained via `ADD` counter transactions with idempotency (read-before-write fast path + an `attribute_not_exists`/`attribute_exists` guard on the like record, run via `TryExecuteTransactWriteAsync` — a concurrent double like/unlike cancels the whole loser transaction, counters and activity included) (`LikeRepository` / `AlbumLikeRepository`). Detail reads return `likedByMe` to any authorized viewer and `likeCount` to the owner only. Album likes add `POST /albums/{id}/like`, `GET /albums/{id}/likes` (owner), `GET /albums/liked` (Library section); album likes are gated on album access (owner or recipient) and cleaned up on album deletion. Losing access (unshare / remove from library) leaves a like in place — it still counts and is still there if re-shared — but the liker's Liked lists hide what they can't open (`GET /playlists/likes` and `GET /albums/liked` both filter by access in the handler). Playlists have no likes (they're private).
- **Albums** contain only the owner's own tracks and are the bulk-sharing mechanism (album share records also carry `GSI2SK=SENDER#{owner}#DATE#…` so `GET /users/{username}/albums/shared` lists one sender's albums shared with the caller, mirroring `GET /users/{username}/shared` for tracks): sharing an album grants recipients access to all its tracks via per-(track×recipient×album) grant records (`SHARED#{user}#ALBUM#{id}`, no GSI keys). Membership is live (adds fan out to existing recipients, removals revoke). Unshare/delete only touches `…#ALBUM#{id}` keys, so direct `SharedTrack` records always survive.
- **Share captions & re-share (upsert)**: both `POST /tracks/{id}/share` and `POST /albums/{id}/share` take an optional `caption` (≤300, sanitised by the validation service) that lives on the per-recipient share record (`SharedTrackDataModel.Caption` / `AlbumShareDataModel.Caption`) and the feed item, surfacing on the shared-with lists and `/feed`. A share is an **upsert of one (target × recipient) row** — never a duplicate. The Lambdas pass the full `validatedAdds` (no pre-dedup); `ShareTrackAsync`/`ShareAlbumAsync` write **every** recipient in `add` (deliberate user action ⇒ always applied): a *new* recipient gets the full share (record + album grants + feed + activity + `shareCount +1`); an *existing* recipient is overwritten with the request's caption + a fresh `sharedAt` (resurfaces the feed/shared-list + a new activity item), grants untouched, `shareCount` unchanged. There is no same-caption short-circuit — re-sharing always resurfaces, and re-sharing without a caption overwrites the stored caption to null (send the caption to keep it). A recipient in both `add` and `remove` → remove wins. Only genuinely-new recipients move `shareCount`.
- **Counters**: albums carry `trackCount`/`totalDurationSeconds`/`shareCount`, playlists `trackCount`/`totalDurationSeconds` (on the likes playlist maintained by the like/unlike transaction — like records denormalize `duration` so unlike can decrement), tracks `shareCount` — all denormalized via `CounterExpressions.Add` `ADD` transactions, maintained on create/add/remove/share. `shareCount` (and track/album `likeCount`) are owner-only in responses; handlers null them for non-owners. Memberships denormalize `duration` so removals reconcile totals even for deleted tracks. `GET /albums/{id}/recipients` and `GET /tracks/{id}/recipients` (owner-only) return hydrated recipient `UserSummary`s for avatar stacks / manage-access.
- **Track editing & ordering**: memberships carry an explicit rank (`GSI1SK=ORDER#{rank}`, zero-padded, spaced 10 apart; required because Query sorts only by sort key), reads page ascending. Playlists are edited by *gestures*: `POST /playlists/{id}/tracks/{trackId}` adds one track (access-checked, sets `addedAt`, appends at max+10; re-adding an existing member is a no-op keeping position and `addedAt`), `DELETE /playlists/{id}/tracks/{trackId}` removes one (idempotent; deliberately no access check so revoked/deleted placeholders stay removable), and `PUT /playlists/{id}/tracks` `{trackIds}` (≤500) is the declarative reorder+remove save — every id must be a current member (adds only via the POST, keeping `addedAt` honest), omitted members are removed, ranks are rewritten 10/20/30… in list order with `addedAt` preserved. Albums are edited in *sessions*: `PUT /albums/{id}/tracks` `{trackIds}` (≤50, own tracks only, empty list clears) is the album's only track endpoint — the submitted list becomes the tracklist (new ids fan out grants to existing recipients, dropped ids revoke theirs, kept ids re-rank only). Both PUTs are last-write-wins on concurrent stale saves. The likes playlist rejects all of these (membership and like-history order are managed via the like endpoint).
- **Track access rule** (single source: `ISharedTrackRepository.IsTrackAccessibleToUser`): owner OR direct share OR album grant. Use it for anything gated on track access. Its listing form is `GET /tracks/library` (`GetLibraryTracksAsync`: own + direct + every track in every shared album, deduped, unpaged) — what web search indexes, so album tracks are searchable.
- **Share links** (`api/Lambda/Link/`, `docs/data-model/links.md`): an owner makes a link for a track or album (`POST /links {kind, targetId, expiresIn: 24h|7d|30d, allowPreview, caption?}` — the caption shows on the invite screen and becomes the share's caption on accept; `LINK#{token}`/`META`, 22-char base64url token, listed per item on GSI3 `LINKS#{KIND}#{id}`); whoever holds it can accept it (`POST /links/{token}/accept`), which **runs the ordinary share upsert** with `add: [caller]` — so they become a normal recipient (access, feed, Shared with, Remove from my library, `shareCount` unchanged) — after a guarded claim (`ADD acceptedCount` only while not revoked and not expired, run before the share so a racing revoke wins). The accept skips `GetValidatedRecipientsAsync` (their own choice — `incomingShares` doesn't apply) and writes no "shared with you" activity (`notifyRecipients: false` on `ShareTrackAsync`/`ShareAlbumAsync`). Revoking (`DELETE /links/{token}`, undo via `POST …/restore`) stops new people joining; people who already accepted keep access. `GET /links/{token}` is the **public** invite preview (`VALID` with sender/item/tracks + preview URLs, `EXPIRED` with only the sender, `UNAVAILABLE` identical for revoked/unknown/deleted); `GET /links/{token}/viewer` (signed in) says `OWN`/`ALREADY_HAVE`/`NONE`. Previews: tracks over 30s play a 30s clip (`processed/{trackId}/preview.m4a`, cut in `ProcessTrackLambda`), tracks of 30s or less play in full; 10-minute presigned URLs, only when `allowPreview` (default on). Deleting a track/album deletes its links.
- **Remove from my library** (recipient-side, the mirror of the owner's unshare): `DELETE /tracks/shared/{trackId}` (`RemoveTrackFromLibraryAsync`) drops only the caller's direct `SharedTrack` record (+ its feed item) and `DELETE /albums/shared/{albumId}` (`RemoveAlbumFromLibraryAsync`) drops only the caller's album-share record + this-recipient album grants (+ feed item). Both are idempotent (no-op if the caller has no share; the share delete + feed delete + counter run as one transaction guarded on the share still existing, so concurrent double-removes decrement once) and decrement the owner's `shareCount` by 1 (keeps it equal to the live record count, so the re-share upsert — which treats a missing record as new — stays consistent). Because the two footprints are disjoint (`SHARED#{user}` vs `SHARED#{user}#ALBUM#{id}`), removing a track never touches album grants and removing an album never touches direct shares: a track that is **both** directly shared **and** in a shared album survives removal of either one, staying accessible via the other. Neither touches the "X shared with you" activity item (aged out by TTL like other unshares).
- **Home feed**: `FeedItem` (`FEED#{recipient}`, deterministic base SK `{TYPE}#{targetId}`) unifies tracks + albums shared with a user into one partition, projected into two date sorts: GSI1 (`DATE#{ts}`, all types interleaved) and GSI2 (`{TYPE}#DATE#{ts}`, one type isolated by a `begins_with` key condition — no `FilterExpression`). Written in the same batch/transaction as every share path (upload `sharedWith`, track share, album share) via the `FeedItems` helper and removed on every unshare/delete. `GET /feed` reads GSI1 (no `type` param) or GSI2 (`type=TRACK|ALBUM`) and hydrates track/album summaries + sender. Display-only, so feed drift on partial failure is tolerated like counters.
- **Activity feed**: per-recipient `ActivityItem` (`ACTIVITY#{recipient}`, descending `DATE#{ts}#{shortId}`, 90-day TTL) written recipient-perspective in the triggering write (via `ActivityItems`) on track/album-like (→ owner, no self-echo), track/album share (→ recipients), and **follow** (`USER_FOLLOWED` → followed user, `USER` target = the follower with no name to hydrate; self-follow is a 400); album-track-adds grant access silently, no activity. `GET /activity` is a **live snapshot, not an event log**: it hydrates actor + target name and keeps a row only if the actor resolves, and (for like/share rows) the target resolves **and the exact relationship record that produced it still exists** (`KeyProbeDataModel` liveness probe of the direct `SHARED#{viewer}`/`LIKE#{actor}` record — *not* general access — whose `likedAt`/`sharedAt` must equal the row's `createdAt`, both written from the same `now`; so after unlike→re-like or a re-share only the newest row shows, older rows don't revive against the recreated key). So unshare/unlike/remove/delete all drop the row at read time; rows are only physically deleted for **follow activity** on unfollow: its SK is deterministic (`DATE#{followTs}#FOLLOW#{follower}`, no random `shortId`, built by `ActivityItems.BuildFollow`) so `UnfollowUser` can reconstruct + keyed-delete it from the follow record's `CreatedAt`; follow/unfollow write the activity as a 4th transaction part alongside the counter updates. `activitySeenAt` (bumped by `POST /me/activity-seen`, private, lives on `ActivityRepository`) badges unread. Listen-analytics events can slot into this entity later.
- **Resume progress**: `UserProgress` (`USER#{u}` / `PROGRESS#LATEST`, 30-day `expiresAt` TTL) is a single per-user resume slot, heartbeat-upserted via `PUT /me/progress` (any context overwrites it); `{completed: true}` deletes it when playback finishes so finished things stop offering to resume. `GET /me/progress` returns it if its track still resolves + is accessible (204 otherwise) — the app-open restore point, carrying `contextType`/`contextId`/`trackId`/`positionSeconds`. `lastSeenAt` on the profile (bumped by `POST /me/seen`, private to the owner) drives the new-since-last-visit divider client-side.
- **Incoming-shares setting**: each profile carries `incomingShares` (`EVERYONE` — default, written at signup — / `FOLLOWING` / `NONE`), set via `POST /profile/update`; unlike the other profile fields, omitting it (or sending null) leaves the stored setting unchanged. Enforced only in `GetValidatedRecipientsAsync` (the choke point for upload `sharedWith`, track share, album share): `FOLLOWING` requires the *recipient* to follow the sender at share time; recipients who don't accept are silently dropped like unknown usernames, so senders can't probe the setting. Existing shares/grants are never revoked by changing it, and album membership fan-out to existing recipients is deliberately not re-validated.
- **Fan-out writes** use `IDynamoDBService.CreateBatchWritePart`/`ExecuteBatchWriteAsync` (SDK chunks to 25 + retries). Ordering rule: grants first, authoritative record (share/membership/meta) last, so failed operations retry cleanly. Limits: 50 tracks per album; recipients are capped per request only (≤50 in a share call's `add`/`remove`, ≤50 upload `sharedWith`), never in total. **Known ceiling:** fan-out runs in-line in the request Lambda (30s), fine for small audiences but not thousands of recipients — if audiences get big, move it to a queue or Step Function (see `docs/data-model/README.md` → Fan-out writes).

## Track Upload Pipeline

**Staging uploads (dropbox ownership):** `GET /buckets/dropbox?key={k}` presigns a PUT for `{username}/{k}` — the server prefixes the caller's username (`Domain/DropboxKeys`) and returns `{url, key}`; clients send that returned `key` as `audioKey`/`imageKey`. Every consumer rejects a staged key outside the caller's prefix with a 400 ("You can only use files you uploaded."): `ValidateUploadedAudioAsync(audioKey, username)` for audio, and `ImageService.ProcessImageAsync(ownerUsername, …)` for every cover/profile image (`UploadTrackLambda` also checks the track cover's prefix up front).

`POST /tracks/upload` → `UploadTrackLambda` validates the request (title, audio key, recipients), verifies the staged audio object exists and is ≤300MB (`ITrackValidationService.ValidateUploadedAudioAsync` — HeadObject, synchronous 400 on failure; images are capped at 20MB inside `ImageService`), mints the `trackId`, writes an upload-status record (`USER#{user}` / `UPLOAD#{trackId}`, status `PROCESSING`, 24h TTL via the table's `expiresAt` attribute), then calls `StartExecutionAsync` on the `UploadTrackStateMachine` (Standard — Express's hard 5-minute cap killed long encodes mid-flight; the binding limit is now `ProcessTrackLambda`'s 15-minute timeout, and the function runs at 1792MB for a full vCPU since the audio encoder is effectively single-threaded, with 10GB ephemeral storage for the input file + encoded output in `/tmp`) and returns `202 Accepted` with `{trackId, status}`. The state machine invokes `ProcessTrackLambda`, which downloads the audio from the dropbox bucket, probes it with ffprobe and rejects tracks longer than 24 hours (`AudioService.MaxDurationHours` — checked between probe and the expensive ffmpeg re-encode; when ffprobe reports no duration (`N/A`) the encode is capped with `-t` just past the limit and the output's duration is checked instead, so an unknown length never reads as 0; may become subscription-tier-dependent later), re-encodes it to a single continuous AAC file (`-c:a aac -b:a 192k -movflags +faststart`, via ffmpeg's built-in native `aac` encoder — no extra layer) uploaded to the private bucket as `processed/{trackId}/audio.m4a` (the source file is archived alongside as `processed/{trackId}/original`, only after a successful encode; for tracks over 30s a 30s share-link preview clip is cut from the encoded file to `processed/{trackId}/preview.m4a`, part of processing like the encode itself), writes the `Track` + `SharedTrack` records transactionally, and marks the status `COMPLETE` — or `FAILED` with a user-safe reason (`ArgumentException` messages pass through, e.g. "not an audio file" or the duration limit; anything else becomes "Audio processing failed."). Clients poll `GET /tracks/uploads/{trackId}` (`GetUploadStatusLambda`) to observe the outcome. If the Lambda dies without reaching its catch block (OOM/timeout), the status sticks at `PROCESSING` — clients should treat a stale `PROCESSING` as failed.

Cross-stack wiring in `Program.cs`: `sfn.UploadTrackStateMachine.GrantStartExecution(lambda.UploadTrackFunction)` and `lambda.UploadTrackFunction.AddEnvironment("STATE_MACHINE_ARN", ...)`.

## DynamoDB Single-Table Design

Table: `melo-melo-table-{env}` with PK/SK composite keys, GSI1 (`GSI1PK`/`GSI1SK`), GSI2 (`GSI1PK`/`GSI2SK` — shares the hash key with GSI1 but sorts differently, so an item projected into both indices carries a single `GSI1PK` attribute and two sort attributes), and GSI3 (`GSI3PK`/`GSI3SK` — independent keys; used for the owner's newest-first listings of tracks (`USER#{u}`), playlists (`PLAYLISTS#{u}` — the likes playlist carries a max sentinel date so it always sorts first), albums (`ALBUMS#{u}`), and followers (`FOLLOWERS#{u}`), plus the username search index on the profile item (`USERS` / `USERNAME#{lowercased username}`, queried alphabetically by `GET /users/search?q=` with `begins_with`; pre-existing profiles need `scripts/backfill-user-search-keys.sh`)).

`IDynamoDBService.QueryPaginatedAsync` maps `indexName` → key attributes: `"GSI1"` → `(GSI1PK, GSI1SK)`, `"GSI2"` → `(GSI1PK, GSI2SK)`, `"GSI3"` → `(GSI3PK, GSI3SK)`, `null` → `(PK, SK)`.

**Adding a GSI requires three code changes** (the schema is registered manually for AOT — no runtime `DescribeTable`): the CDK table in `infra/DataStack.cs`, the `TableBuilder` registration in `DynamoDBService`'s constructor, and the `GetKeyAttributeNames` mapping. Missing the `TableBuilder` entry fails at runtime with "Unable to locate index".

Full schema, key patterns, and every API's access pattern chain are documented in [`docs/data-model/`](docs/data-model/README.md), split by domain (users, tracks, playlists, albums, feed, activity) with cross-cutting rules in the index.

## Environment Configuration

The environment is picked by `-c env=…` or the `ENVIRONMENT` env var (default "dev") and names every stack/resource (`…-{env}`). Everything that differs per environment lives in **`cdk.json` → `context.environments.{dev|prod}`**: `removalPolicy` (`retain`/`destroy`), `autoDeleteObjects`, `pointInTimeRecovery` (prod on), `uploadCorsOrigins` (dropbox PUT CORS), `domain` (`{name, hostedZoneId}` — web-stack's custom domain + Route53 alias; null → CloudFront domain; needs `WEB_CERTIFICATE_ARN`), `email` (Cognito's SES sender; null → Cognito's built-in), `linkPreviewThrottle` (`GET /links/{token}` rate/burst). `infra/EnvConfig.cs` loads it into a typed record that `BaseStack` exposes as `Config` (`Env` = its name, `DeletionPolicy` = its removal policy) — read settings from there, never `Env == "prod"`. An environment missing from `cdk.json` (e.g. a typo'd `ENVIRONMENT=prd`) or an unknown key fails the synth rather than falling back to dev's destroy settings. Adding an environment = a new block in `cdk.json`.

## Lambda Layers

Binary layers (ffmpeg, ffprobe) are sourced from zip files at `api/Lambda/Layers/`. They are created as CDK `LayerVersion` assets in `StepFunctionStack.cs` and attached to `ProcessTrackLambda`. Binaries are referenced from `/opt/bin/{ffmpeg|ffprobe}` at runtime — do not use ARN environment variables for these layers.

The zips MUST contain **linux-arm64 (aarch64) static binaries** at the path `bin/<name>` inside the zip (so they land at `/opt/bin/<name>`). x86_64 binaries fail at runtime with "Exec format error" because the Lambda runs on ARM64. There is no separate encoder layer — the AAC encode uses ffmpeg's built-in native `aac` encoder.

## Validation Pattern

Input validation follows a hexagonal pattern:
- **Port**: `ITrackValidationService`, `IUserValidationService`, `IAlbumValidationService`, `IPlaylistValidationService` in `api/Ports/Validation/`
- **Adapter**: `TrackValidationService`, `UserValidationService`, `AlbumValidationService`, `PlaylistValidationService` in `api/Adapters/Validation/` using FluentValidation
- All services sanitise inputs (trim, collapse whitespace/newlines) before validating, mutate the request in place, and throw `ArgumentException` with a user-safe message (handlers catch it → 400)
- HTTP request records (`CreateAlbumRequest`, `UpdateTrackRequest`, …) live in `api/Domain/` alongside their entities so the Adapters-layer validators can see them
- `IUserRepository.GetValidatedRecipientsAsync` filters a `sharedWith` list to usernames that exist in DynamoDB AND accept shares from the sender (it lives on the repository because it owns the `USER#`/`PROFILE` key format). It lowercases what was typed, so matching is one exact-key BatchGet (see the lowercase-usernames convention).
- Shared sanitisation helpers live in `Adapters/Validation/InputSanitiser.cs` — use them instead of duplicating regexes

## Pagination

- Paginated reads return `PaginatedResult<T>` (`api/Domain/PaginatedResult.cs`) with `Items` and a nullable `NextCursor`.
- `IDynamoDBService.QueryPaginatedAsync` takes `pageSize` + `paginationToken` and returns `(Items, NextToken)`. Default is `scanIndexForward: false` (newest first).
- Cursors are opaque **base64url** strings (encoded/decoded inside `QueryPaginatedAsync`) — the raw SDK token is JSON with `#`/`{`/`"` characters that break unencoded query strings.
- HTTP handlers read `cursor` from `QueryStringParameters` and forward it verbatim; when there are no more pages, `NextCursor` is `null`.
- The library listings (`GET /tracks`, `/tracks/shared`, `/playlists`, `/albums`, `/albums/shared`, `/albums/liked`), `GET /users/search` and `GET /playlists/{id}` (the web app pulls a whole playlist 100 at a time to search/sort it) accept an optional `limit` query param (default 10, clamped to 1–100 by `BaseLambdaFunctionHandler.ParseLimit`) so the client can pull larger pages for client-side search; other paginated endpoints keep fixed page sizes.
- See `GetUserTracksLambda` + `TrackRepository.GetTracksByUsername` for the canonical pattern.

## Key Conventions

- All Lambdas use `PROVIDED_AL2023` runtime with `PublishAot: true` (native AOT, ARM64, 512MB memory)
- JSON serialization via `System.Text.Json` with AOT source-generated contexts
- Amazon.Lambda.Annotations for attribute-based routing and dependency injection
- HTTP responses: `202 Accepted` for async operations (Step Functions), `200 Ok` for reads, `201 Created` for synchronous resource creation
- **Repository structure** (`Adapters/Repositories/`): each repository owns its records' key formats and cleans up after itself — `DeleteTrackAsync` delegates to `ILikeRepository.DeleteLikesForTrackAsync` (also decrements likers' likes playlists), `ISharedTrackRepository.DeleteSharesForTrackAsync` and `IUploadStatusRepository.DeleteAsync`; `DeleteAlbumAsync` to `IAlbumShareRepository.DeleteAllSharesAsync` (grants first), `IAlbumLikeRepository.DeleteLikesForAlbumAsync`, `IAlbumTracklistRepository.DeleteAllTracksAsync`, meta last. Shared internal helpers instead of per-repo copies: `Keys` (meta-item keys: profile/track/album/playlist), `CounterUpdates.CounterUpdate<T>` (every denormalized-counter `ADD` part), `ProfileLookup` (deduped profile BatchGet + ordered summaries), `AlbumRecords` (album membership/share queries, the per-track **grants** both tracklist and sharing fan out, album counters), `FollowRecords` (the follow-record lookup shared by follows and recipient validation), plus the existing `TrackBatchLookup`.
- **Summary DTOs** (`api/Domain/Summaries.cs`): every list/row context serializes `UserSummary` (`{username, displayName, imageUrl, imageBgColor}`), `TrackSummary`, or `AlbumSummary` (both with a non-null `likedByMe` + `owner: UserSummary`); full `User`/`Track`/`Album` appear only on their detail GETs (+ create/update echoes). Owner-only counts (`likeCount`/`shareCount`) exist only on the full objects. `TrackBatchLookup.GetTrackSummariesAsync` is the shared track-row join (tracks + deduped owners + viewer like-status in one parallel BatchGet round); `AlbumLikeRepository.GetLikedAlbumIdsAsync` is the album equivalent.
- The track title is JSON `name` everywhere (upload request, update request, Track/TrackSummary responses); the DynamoDB attribute stays `trackName`.
- All JSON is camelCase, including `ErrorResponse` (`{statusCode, message, error}`).
- **Usernames are lowercase everywhere** they're stored, keyed or compared — one spelling, so every lookup is an exact key. Normalised at the boundaries: `GetCallerUsername` lowercases the JWT claim, handlers run `{username}` path params and body usernames (share `add`/`remove`) through `BaseLambdaFunctionHandler.NormaliseUsername`, `GetValidatedRecipientsAsync` lowercases recipients, and sign-up accepts any casing (`^[a-zA-Z0-9._]{2,30}$`) and PostConfirmation saves the username lowercased (`displayName` defaults to that same lowercase username) — one version, no casing variants. Cognito sign-in is case-insensitive, and its claim is lowercased on every request.
- **Catch-all 500s return `InternalError()`** (generic "Something went wrong" message) — never `ex.Message`, which can carry AWS internals; the exception is logged via `context.Logger` instead.
- **Unit tests** live in `api/Tests/Adapters.Tests` (xUnit v3 on Microsoft.Testing.Platform — opted in by the root `global.json`, so use `dotnet test --project …`; NSubstitute for single dependencies; **FluentAssertions 7.x** (`.Should()`, global using) — pinned below 8 because v8 needs a paid licence for commercial use; only `Assert.Skip` remains from xUnit, for the DynamoDB Local runtime skip). Three layers: `Pure/` (key/expression builders, `DropboxKeys`, `InputSanitiser`), `Validation/` (the four validation services), and `Repositories/` — the **real** `DynamoDBService` + repositories against DynamoDB Local via `DynamoDbLocalFixture` (creates a throwaway table mirroring `DataStack`; skips when `DYNAMODB_LOCAL_URL`, default `http://localhost:8000`, is unreachable unless `REQUIRE_DYNAMODB_LOCAL=1`). Seed through the `Seed` helper (same writes as production) and use fresh GUID names per test. `api/Tests/**` is excluded from Lambda assets. CI (`.github/workflows/ci.yml`) runs them as the `unit-tests` job (DynamoDB Local service container); the `e2e` job `needs` it, so a failure stops the deploy. **Handler tests** live in `api/Tests/Lambda.Tests`: every Lambda's `FunctionHandler` called directly with NSubstitute-mocked ports, asserting auth (401), ownership/access (404, never 403 except private follower lists), validation (400), response shapes/owner-only field stripping, and the calls made to repositories (`Received.InOrder` where order matters). Because every Lambda assembly is named `bootstrap`, the project can't reference them — it **compiles their `Function.cs` + `{Name}JsonContext.cs` directly** (Startup/AssemblyInfo excluded, Annotations generator stripped). That's why each Lambda's JSON context has a **unique name** (`{LambdaName-without-"Lambda"}JsonContext`, e.g. `GetAlbumJsonContext`): the STJ source generator can't emit two same-named contexts into one compilation. New Lambdas must follow that naming and put `using {Namespace};` in `AssemblyInfo.cs` so the runtime serializer is the Lambda's own context. Helpers: `Support/Http` (`Http.As(user, query)` / `Http.Anonymous()`, `ShouldHaveStatus`, `Json()`), `Support/Fakes`, `Support/TestLambdaContext`. The Playwright e2e suite (`e2e/`) covers the HTTP surface against a deployed stack.
